## 🔴 Critical — интерактивная карта зависит от внешнего API без кэша и без fallback

**Файл:** `sections/map.js:274-289` (`fetchDistrictBoundary`), вызывается из `_initLeaflet` (строка 106-123).

Каждая загрузка главной страницы делает **клиентский** запрос к публичному `nominatim.openstreetmap.org` за геометрией границы района — без какого-либо кэша (ни `localStorage`, ни серверного прокси/файла с сохранённой геометрией). Nominatim официально ограничивает использование (≈1 запрос/сек, требует явный User-Agent/Referer, банит при нарушении) — это создано для геокодинга по клику пользователя, а не для вызова на каждой загрузке публичной страницы.

**Подтверждено дважды независимо:**
1. Playwright-тест поймал реальную ошибку в консоли браузера: `Access to fetch at 'https://nominatim.openstreetmap.org/...' ... has been blocked by CORS policy`.
2. Тот же самый сбой воспроизвёлся отдельно в независимом прогоне Lighthouse (`errors-in-console` = 0).

Оба сбоя произошли **не под нагрузкой**, а при обычном тестировании в течение часа — то есть порог срабатывания у Nominatim довольно низкий.

**Что происходит при сбое:** `try { districtFeature = await fetchDistrictBoundary(); } catch (e) {}` → `if (!districtFeature) return;` — функция тихо завершается. Пользователь видит пустой блок карты вместо ошибки или заглушки — весь раздел «Интерактивная карта» перестаёт работать без какой-либо видимой причины и без возможности повторить попытку.

**Рекомендация:** сохранить геометрию границы района один раз (она не меняется) в `data/map.json` или отдельный статический файл, отдавать её с собственного сервера — полностью убрать рантайм-зависимость от Nominatim с публичной страницы.

### 🟡 Производительность (Performance 51–78 на публичных страницах)
Повторяющиеся проблемы почти на каждой странице:
- **Render-blocking requests** — Google Fonts и Leaflet CSS/JS подключены в `<head>` без `defer`/`preload`, блокируют первую отрисовку (до ~3.1 сек оценочной экономии на главной).
- **Image delivery** — 761–808 KiB потенциальной экономии на страницу: изображения не оптимизированы под реальный размер показа/формат (WebP).
- **Cache lifetimes** — картинки из `uploads/` кэшируются 7 дней (`max-age=604800`, уже настроено в `index.js`), Lighthouse хочет дольше; учитывая, что файлы без версионирования в имени, увеличивать TTL стоит только вместе с механизмом инвалидации кэша при замене файла.
- **Layout shifts (CLS)** — на `team.html`, `documents.html`, `all-numbers.html`, `feedback.html` — 2 сдвига макета, вероятно из-за перехода skeleton-заглушки → реальный контент без зарезервированной высоты.
- **mainThread-work / forced-reflow** — на главной, вероятно из-за инициализации Leaflet + анимации счётчиков одновременно с рендером секций.

### 🟡 «Мерцание» галереи из-за `loading="lazy"` в бегущей строке
`sections/gallery.js:25` (а также `news.js:110`, `achievements.js:99`) используют `loading="lazy"` на картинках. Для карточек в обычном скролле это правильно и полезно. Но для `.gallery-marquee` — бесконечно бегущей CSS-анимированной ленты — это создаёт видимый баг: картинки, ещё не долистанные лентой до зоны предзагрузки браузера, показываются пустыми/серыми и всплывают с задержкой уже во время просмотра, а не до него. Файлы не битые (подтверждено), просто лениво грузятся в неподходящем для карусели месте. Рекомендация: убрать `loading="lazy"` конкретно на `.gallery-marquee-set img` (там и так всего 10 картинок, дублированных дважды для бесшовной прокрутки — предзагрузка не станет проблемой).
